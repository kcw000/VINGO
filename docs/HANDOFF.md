## 制作コンセプトと経緯

VINGOは、音楽イベントの待ち時間を楽しみ、参加者同士の会話や知らない曲への興味を増やすための楽曲ビンゴ。景品の厳密な抽選管理や不正防止システムではなく、会場体験を豊かにするお楽しみ企画として作られた。

Google Antigravityでボカホール専用版を制作し、実際のイベントで利用。その後、ビタミンV2など別イベントでも使えるよう、イベント名・主催者・SNS・候補曲の設定と共有リンクを備えた汎用版へ発展した。今後の改善・保守をCodexへ移し、完成済みの機能・デザインを維持することが今回の目的である。

## 現行の構成と画面

`index.html` 内にCSS、HTML、JavaScriptがある。初期曲データ `songsMaster`、ゲームの `state`、テーマ処理、上部のイベント名編集、`VingoSettings`、`SettingsModal` が主要な構成要素。外部JSライブラリ、API通信、バックエンド、Service Workerは実装されていない。

画面は、タイトル→イベント名→テーマ→共有リンク貼り付け→ステップ表示→状態→ランダム・確定→ヒント→VINGO表示・演出再表示→カード→SNS案内→リセット・遊び方の順。設定ボタンは固定配置。VINGOバナーはDOM上ではカードより上にある。

7テーマはシンプル、ミク、リン、レン、ルカ、メイコ、カイト。テーマはカード内容を変えず、色を切り替える。QR参加と専用スクショモードは廃止済みで、関連する古いコメントやCSSが残っていても復活の根拠にしない。

## ゲーム仕様

- 初期候補は276曲で、初期曲名に重複はない。設定があればその候補曲を使う。
- `randomize()` はFisher–Yates方式で配列をシャッフルし、先頭9件を抽選する。同じ配列要素は重複しないが、登録した曲名の重複は除去しない。
- 確定前は引き直し可能。`lock()` 後は抽選を止め、マスのチェックを許可する。
- `checkBingo()` は横3・縦3・斜め2の8ラインを判定する。チェック解除後に成立ラインが0本になると成立状態も解除される。他の成立ラインが残る場合はVINGOを維持する。
- 最初の成立時に端末の `new Date()` を記録し、年月日・時分で表示する。成立を解除して再成立しても、盤面リセット等までは最初の日時が残る。
- 成立時はバナー、紙吹雪・クラッカー風演出、SNS案内を表示する。「演出をもう一度見る」も実装されている。
- 成立日時は端末の時計に依存し、秒表示やサーバーによる証明はない。厳密な先着順位の根拠にはできない。
- 設定を保存しても既存カードは即時に作り直されない。確定中は次回ランダムから曲リストを反映する案内が出る。

参照：[ゲーム処理](https://github.com/kcw000/VINGO/blob/308d4726ab6400a557e2f3c1b9dccef115069caf/index.html#L2396)

## 主催者設定と共有データ

設定画面のイベント名は `maxlength=30`、主催者名は `maxlength=20`。これは入力UIの制限であり、共有データのすべての項目に同じ制限が実装されているわけではない。

保存するJSONの代表例（架空の設定）：

```json
{
  "v": 1,
  "eventName": "テストイベント",
  "organizerName": "テスト主催者",
  "xTarget": "",
  "igTarget": "",
  "songs": ["曲1", "曲2", "曲3", "曲4", "曲5", "曲6", "曲7", "曲8", "曲9"]
}
```

| 項目 | 現行の意味・挙動 |
|---|---|
| `v` | 生成値は1。読み込みで未指定なら1を補うが、未対応版を拒否する処理はない |
| `eventName` | デフォルトは `VINGO EVENT`。読み込み検証では長い値を30まで切り詰めるが型確認は不十分 |
| `organizerName` | SNS案内の宛先名。空欄なら名前部分を省略。読み込み時の型・20文字制限は不十分 |
| `xTarget` / `igTarget` | ユーザー名またはURL。空欄なら対応ボタンを隠す。初期値には制作者の送付先が入る |
| `songs` | 曲名配列。初期設定は `null` で内蔵276曲を使用する |

入力された候補曲は行単位で前後空白・空行を除く。保存時は9〜500件を受け付ける一方、画面案内は9〜300曲。共有読み込み時は配列内の空・非文字列を除き、300件超を切り詰め、9件未満なら拒否する。この不一致はBUG-001で管理する。

共有はJSONをUTF-8相当のバイト列からBase64URLへ変換し、`?v=1&cfg=...` を現在のorigin＋pathnameに付ける。圧縮・暗号化・署名はない。候補曲などの設定はリンクを知る人が復元できるため、秘密情報を入れない。

読み込みは `cfg`、互換キーの `c`、`settings` を受け付ける。URL外側の `v` は読み込み判定に使用していない。成功時は設定を保存・画面反映し、クエリを除去して約1.5秒後に再読み込みする。貼り付け画面はURLのほか、URLではない生のcfg文字列も処理できる。

共有ボタンは保存済み設定から生成するため、未保存の入力は共有されない。初期設定のまま生成すると `songs: null` が入る。`getCurrentSettingsForExport()` は初期曲を配列へ展開する関数だが、現在の共有画面はこの関数を使っていない。

参照：[VingoSettings](https://github.com/kcw000/VINGO/blob/308d4726ab6400a557e2f3c1b9dccef115069caf/index.html#L3123)・[URL適用処理](https://github.com/kcw000/VINGO/blob/308d4726ab6400a557e2f3c1b9dccef115069caf/index.html#L3323)

## 保存とリセット

localStorageは同一originのブラウザ保存領域であり、端末や別ブラウザに同期されない。イベント設定は1件分で、新しい共有設定の読み込みは既存設定を置き換える。

| 保存キー／状態 | 内容 | 再読み込み | 盤面リセット | 設定の「全てリセット」 |
|---|---|---|---|---|
| `vingo_theme` | 選択テーマ | 残る | 残る | 残る |
| `vingo_settings_json` | イベント・主催者・SNS・曲リスト | 残る | 残る | 削除 |
| `vingo_event_name` | 上部編集用のイベント名 | キーは残るが設定JSONの値で表示が戻る場合あり | 残る | 削除 |
| メモリ内 `state` | カード、確定、チェック、成立ライン・日時、演出状態 | 失われる | 初期化 | 再読み込みで初期化 |

上部のイベント名リセットは `vingo_event_name` のみ削除する。設定JSONのイベント名は削除されず、再読み込みや共有で不一致が起きる。設定の読み書きは例外を握りつぶす箇所があり、保存失敗を成功表示してしまう。

## SNSと演出の重なり

X・Instagramの設定値をプロフィール等のリンクに変換し、別タブで開く。主催者名は案内文へ反映する。空欄のSNSボタンは隠れるが、SNS案内欄自体はVINGO成立時に表示される。画像添付やDM送信は参加者が行う。URLの送付先ドメインが期待どおりかも検証対象にする。

演出には `pointer-events: none` が指定され、モーダル表示中は `body.modal-open` によりVINGO表示・SNS案内・演出を隠す。主なレイヤー値は通常UI 10、重要ボタン20、紙吹雪3000、演出文字3500、モーダル背景9000、本体9100、通知9200。個別の指定もあるため、変数だけを見て安全と判断しない。

### 盤面消失の優先度評価

IMP-001は「中・将来」ではなく、次のイベント運用に向けた高優先度の改善とすることを提案する。誤って再読み込みしただけで進行が失われ、元のカードへ戻せないためである。スマホOSによるタブ再読み込みでの発生頻度は未検証だが、手動再読み込みで消えることは確認済み。

ただし、`state` をそのまま保存するだけでは不十分。同じ端末で別イベントのリンクを開いたときに、前のカードを新しい主催者へ送ってしまう恐れがある。少なくとも次を設計してから実装する。

- イベント設定とカードを結び付ける識別方法。名称だけで同一イベントと判断しない。
- 抽選曲と順序、確定状態、チェック、成立日時の保存対象と保存タイミング。
- 別イベント読み込み、設定編集、盤面／全設定リセット時に何を消すか。
- 保存不可・破損・旧形式・複数タブ時の復旧と案内。
- 復元直後に演出を再生するか、成立日時をどう保つか。

当面の運用案は、再読み込みを避ける案内と必要時のスクリーンショット。ただしスクリーンショットは盤面復元機能の代わりにはならない。データベースやログインは、端末内の途中再開を実現するための必須条件ではない。

## 調査結果と検証の限界

2026-11-09の初回調査は、一時Chromium 149.0.7827.55、公開版と一致するHTMLを使う隔離環境で実施した。公開URLのHTTP 200、通常の起動、暗色テーマ成立ラインは公開サイトへ直接アクセスした一時ブラウザでも確認した。通常使用中のブラウザの設定は変更していない。

| 項目 | 初回の結果 |
|---|---|
| 標準候補の抽選 | 100回とも9件のIDが重複しない。カスタム曲名の重複排除を保証する結果ではない |
| VINGO判定 | チェック状態512通りを別の行・列・斜め判定と照合し一致 |
| 操作 | 確定、チェック、成立日時、設定保存、リセット、共有リンクの適用・貼付を確認 |
| 演出と設定 | 演出中のモーダル入力が可能。モーダル中にバナー・紙吹雪が非表示 |
| テーマ・幅 | 7テーマの切替、1440 / 768 / 390 / 320pxのページ全体の横あふれなし。視認性はBUG-002等の課題あり |
| 未確認 | iPhone / Android実機、Safari、SNS経由の長いリンク、DM送信、全要素のアクセシビリティ適合 |

架空データ（曲名 `検証用楽曲001` 形式、イベント名「共有テスト」、主催者名「テスト主催者」、SNS空欄）での共有URL全体の文字数は、9曲440、50曲1,588、150曲4,388、300曲8,588。全件が隔離Chromium内で読み込めた。配信サーバー・SNS・実機を通る長いURLの成功を示す結果ではなく、任意の曲名で同じ長さになるわけでもない。

初回の一時検証コード・画像はリポジトリに同梱していない。現時点で、これらを再実行する正式な自動テスト環境はない。Phase 1は文書・Git・本体不変・ローカル起動の確認を行い、初回の全操作試験を再実施したものとして扱わない。
