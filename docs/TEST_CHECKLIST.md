最新の実施記録は末尾の「Phase 3-A」。BUG-003はローカル修正済み・未公開で、過去のPhase 2 / 2.5にある55件・11ケースという数値と未解決表記は当時の結果として残す。

この表の「実施結果」は次回以降に記入する欄で、初期値はすべて未実施。期待結果に将来の修正目標を含む行では、現行の不具合を併記した。「現行」の記述は観測結果であり、不具合を合格させる期待値ではない。既知不具合の再現は受入合格ではない。初回調査の結果は [調査記録](HANDOFF.md#調査結果と検証の限界) に分離している。

改修ごとに対象行を選び、ID・結果・観測内容を実施記録へ追記する。対象外は理由を記録する。アプリ変更では変更箇所と主要機能を回帰確認し、文書だけなら文書・リンク・本体不変を中心に確認する。

結果は「合格」「不合格」「未実施」「対象外（理由）」を用い、既知不具合はIDも記入する。

## 準備

- 専用の一時ブラウザまたはテスト用プロファイルを使う。通常利用中のlocalStorageを消さない。
- [READMEの方法](../README.md#ローカル起動) で起動する。機能検証は原則ローカル、公開確認は許可された範囲で行う。
- 曲名「検証曲001」等を用意する。9・50・150・300・301曲、重複、空行、長い日本語・絵文字を含む別パターンを作る。
- SNSは架空の入力値を使ってリンク先文字列と表示を確認する。実際のDMや投稿は送らない。
- 各テストの前提設定を記録し、別テストの保存値が紛れ込まないようにする。

## 自動テスト環境の導入計画（未実施）

この節はPhase 1で作成した計画の記録。Phase 2では配置と実行方法を具体化しており、現在の手順は [_tests/README.md](../_tests/README.md)、実施内容は末尾の「Phase 2」を参照する。以下のルート配置案や「未導入」の記述を現在の状態と混同しない。

### 推奨構成と依存

JavaScriptの **Playwright Test + Chromium headless shell** を第一段階にする。アプリ本体は静的HTMLのまま、テストだけを開発用依存へ分離する。外部DB・クラウドテスト契約は不要。

導入候補は `@playwright/test` のみ。内部依存はnpmのlockfileで固定し、別のテストランナー・フロントエンドフレームワーク・静的サーバーパッケージは追加しない。実行基盤は対応するNode.jsとnpm（例：Node.js 24系）を用意する。Python 3はREADMEの手動起動で使えるが、自動試験はNode標準ライブラリだけの小さなローカルHTTPサーバーを計画する。

Playwrightの [導入要件](https://playwright.dev/docs/intro) と [ブラウザ管理](https://playwright.dev/docs/browsers) を導入時に再確認し、バージョンを固定する。headless shellだけの導入では画面付き実行はできない。最初の目視確認は通常のブラウザを用い、必要になった時点で通常Chromium／WebKitの追加容量を相談する。Codex等に同梱されたランタイムや既存キャッシュの絶対パスを正式な依存先にはしない。

### 将来追加するファイル案

以下は計画のみ。Phase 1では作成していない。

```text
package.json                 # private:true、devDependencies、テスト用scripts
package-lock.json            # 再現可能な依存バージョン
playwright.config.js         # 一時ブラウザ、localhost、画面幅、失敗時の記録
tests/server.cjs             # Node標準HTTP、127.0.0.1のみで起動
tests/game.spec.js
tests/settings.spec.js
tests/share.spec.js
tests/display.spec.js
tests/fixtures/              # 架空設定・曲リスト
.gitignore                   # node_modules・レポート・一時成果物を除外
```

サーバーは公開サイトと同じ `/VINGO/` 接頭辞でHTMLと画像を配信し、許可したファイルだけを読み取る。`webServer` から起動・終了し、別プロセスの既存サーバーを使い回さず、ポート使用中なら明示的に失敗させる。テストごとに独立したBrowserContextを使い、本番URLや実イベント設定を自動テスト先にしない。

### ディスク容量の目安

2026-11-09に手元の既存ツールを読み取り計測した参考値：Chromium headless shell 約197MiB、通常Chromium 約356MiB、FFmpeg 約3.3MiB、Playwright関連2パッケージ計約12.7MiB。これは新規導入予定版や全OSの保証値ではなく、今回のダウンロード量でもない。

| 構成 | 新規導入時の計画用概算・扱い |
|---|---|
| 推奨：runner＋headless shell | 約200〜400MiB＋npmキャッシュ。Node.js/npm本体が未導入なら別途必要 |
| 通常Chromiumも追加 | さらに数百MiB。最初から両方を入れない |
| WebKit / Firefox追加 | それぞれ数百MiB程度を別途見積もる。まずスマホ重要経路の手動試験を優先 |
| 記録 | スクショ・traceは失敗時のみ、動画は初期無効。保存期間を決め、増え続けないようにする |

既存キャッシュと版が一致する場合に限り再利用できる。別版のブラウザを絶対パス指定で無理に流用する構成にはしない。PlaywrightはApache-2.0で公開され、ローカル実行にサービス利用料は不要。[ライセンス](https://github.com/microsoft/playwright/blob/main/LICENSE)

### 導入・実行方法案

以下は**導入承認後**に、上記の設定・テストファイルを整備した環境で使う手順。先に `package.json` のdevDependenciesへ、承認した `@playwright/test` の正確なバージョンを記載する。現在のリポジトリではまだ実行できない。

```sh
# 初回の導入時。承認済みpackage.jsonを基にlockfileを作成・確認する
npm install
npx playwright install chromium --only-shell

# 別PCでの再現。承認済みのpackage.jsonとlockfileがある状態で実行する
npm ci
npx playwright install chromium --only-shell

# 設定ファイルにchromiumプロジェクトを用意した後に実行する
npx playwright test --project=chromium
```

インストールは承認済みバージョンを採用し、実行時に自動で最新版へ更新しない。Linuxでは対応OSのブラウザ実行依存も必要になるため、導入前に公式の依存条件を確認する。

最初はワーカー数1、再試行0、390pxと1440pxを中心にする。タイマーは待機条件またはテスト用の時計で扱い、長い固定sleepに依存しない。ランダム抽選は候補内・9件・重複なし等の性質を確認し、偶然の並び順を固定の期待値にしない。

### 最低限の自動テスト

Phase 2の優先順は、まず起動と通常のゲーム経路・保存・共有を確認し、次に高優先度のBUG-001〜003、その後BUG-004〜007と表示全体へ広げる。IMP-001は復元設計を合意してから期待結果を確定する。IMP-002のSNS経由・実機確認は自動テストとは別枠で計画する。テスト環境を導入するだけの段階で本体の不具合を修正しない。

1. 起動とJS例外、抽選9件、確定後の引き直し禁止、チェック切替、盤面リセット。
2. VINGOの512通り、複数ライン、成立日時、チェック解除と再成立。
3. 設定保存・再読込、イベント名の両編集経路、SNSのhrefと空欄非表示、各種リセット。
4. 9 / 300 / 301曲、重複・8種類以下、空行、型不正・未対応版、保存失敗。
5. 別BrowserContextへの共有、貼付とURL直接読み込み、設定が一致すること、破損データで既存値を壊さないこと。
6. 演出中のモーダル操作、7テーマの切替、主要幅の横あふれ、成立ラインの色・スクリーンショット。

UI操作を中心とし、512通りなどはブラウザ内で現行の判定関数を検証できる。テストのためだけにアプリ本体へ公開APIを追加しない。期待値は実装のコピーにしない。
